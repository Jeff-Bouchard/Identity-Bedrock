Abstract

Problem. Centralized AI inference services share a common failure surface: provider-revocable API keys, default prompt logging, corporate Terms-of-Service as an operational kill switch, BGP-reachable endpoints that can be geofenced or blocked, and fiat payment rails that are fully traceable. Each of these vectors can individually terminate a user's access to inference.

Solution. This paper specifies a decentralized inference marketplace built on the PrivateNess stack. Service discovery is anchored in Emercoin NVS WORM records (append-only, AuxPoW-hardened). Transport is Skywire mesh (public-key routing, not IP routing). Authentication uses privatenessID chain-anchored identity records. Client-facing billing is denominated in NCH (NESS Coin Hours), settled through the underlying EMC/Coin Hours rail. The entropy layer is grounded in NESS UHE-PRNG (Ultra-High Entropy Pseudo-Random Number Generator), providing bit-for-bit identical, deterministic, bounded randomness across all distributed nodes while still allowing controlled creativity bursts — enabling verifiable, replay-auditable generation without a centralized orchestrator.

Contribution. We define: (1) the WORM XML capability schema ness:worm:inf:1.0; (2) the EmerDNS SRV + CAA discovery and trust protocol; (3) the full ness: namespace hierarchy; and (4) three concrete wiring patterns for connecting any OpenAI-compatible inference client — including Claude-format applications via a litellm proxy and MCP tool server — to sovereign NESS inference nodes. The result: no provider-revocable API keys, no logging infrastructure, no provider kill switch, no DNS-blockable discovery root, and no fiat-facing billing rail. Identity keys remain owner-revocable; what NESS removes is third-party revocation power.

1. Introduction — The Centralized AI Problem

Every major AI inference provider — OpenAI, Anthropic, Together.ai, Replicate, Groq — converges on the same threat model against their users. The threat is not malicious intent; it is structural. The following five properties are inherent to any centralized API architecture:

  • Provider-revocable API keys. Authentication is a credential the provider issues and can revoke. One policy violation, one government subpoena, one corporate decision — the key stops working. The user has no recourse. Identity keys remain owner-revocable; the point here is that NESS removes third-party revocation power from the client path.
  • Prompt logging by default. The provider receives the plaintext prompt. "We don't log" is a Terms-of-Service promise, not a cryptographic guarantee. Every word you send to a centralized inference API is observed and attributable.
  • ToS as the kill switch. The operational contract between user and provider is a unilateral document the provider can change at any time. Specific users, topics, jurisdictions, or use cases can be terminated by policy update.
  • BGP-reachable = geofenceable. api.openai.com resolves to IP addresses on the public internet. Those addresses can be blocked by DNS censorship, firewall rule, or ASN-level filtering. An entire country can be cut off overnight.
  • Fiat payment = traceable. Every inference call is ultimately backed by a credit card, bank transfer, or crypto exchange account linked to a real identity. The financial trail is surveillance infrastructure.

The PrivateNess stack addresses each attack surface structurally — not through better policies, but through architectural elimination. This paper specifies how.

2. NESS UHE-PRNG Foundation

The entropy layer is built on Gibson Research Corporation's Ultra High Entropy Pseudo-Random Number Generator (UHEPRNG). The critical property is cross-node reproducibility: given the same seed, every node in the network produces the exact same sequence of random values without any coordination. UHEPRNG uses a Multiply-With-Carry (MWC) algorithm with a Germain prime multiplier to guarantee full-period coverage of the state space.

2.1 Mash Hash Seed Compression

An arbitrary-length NVS string seed (e.g., "ness-elite-001") is compressed into the UHEPRNG's internal state using the Mash hash function, which provides avalanche properties:

function Mash() {
  let n = 0xefc8249d;
  return function(data) {
    if (data) {
      data = data.toString();
      for (let i = 0; i < data.length; i++) {
        n += data.charCodeAt(i);
        let h = 0.02519603282416938 * n;
        n = h >>> 0;
        h -= n;
        h *= n;
        n = h >>> 0;
        h -= n;
        n += h * 0x100000000; // 2^32
      }
      return (n >>> 0) * 2.3283064365386963e-10; // 2^-32
    } else n = 0xefc8249d;
  };
}

The Mash hash ensures that every bit of the input affects every bit of the output approximately 50% of the time, providing strong avalanche properties for seed-to-state mapping.

2.2 Multiply-With-Carry Generator

The core generator uses Marsaglia's MWC algorithm with a Germain prime multiplier:

function rawprng() {
  if (++p >= o) p = 0;
  let t = 1768863 * s[p] + c * 2.3283064365386963e-10; // 2^-32
  return s[p] = t - (c = t | 0);
}

The multiplier 1768863 is a Germain prime (where 2p+1 is also prime). This property, combined with the MWC algorithm's carry propagation, guarantees that the internal state visits the entire 232 space before repeating — a full period of over 4.29 billion draws. The qualifying MWC multipliers are 187884, 686118, 898134, 1104375, 1250205, 1460910, and 1768863; we use the largest that is < 221.

2.3 Distributed Consensus Property

Key invariant: If two nodes initialize a PRNG with the same seed string, they will produce the exact same floating-point sequence [0,1) for all subsequent draws, independent of platform, CPU architecture, or execution time. This is a consequence of the integer-only arithmetic (no floating-point non-determinism until the final division by 232).

In the Privateness network context: the seed and entropy control parameters (εmax, εmin, λ, α, ω) are stored as an NVS WORM record on Emercoin. Any node reading that record initializes with the identical state. All nodes independently compute identical probabilistic output — distributed consensus without a coordinator and without the communication overhead of sharing outputs. The historical cryptography lineage here is separate: Rompel's STOC 1990 result on one-way functions was later given a complete write-up by Katz and Koo, and then revisited through the inaccessible-entropy/UOWHF line of work in EUROCRYPT 2010.

3. Entropy Control Architecture

Raw PRNG output is not injected directly into the logit space. The NESS entropy control panel implements a compound modulation function that governs how much randomness is injected at each generation step t, with three interlocking mechanisms:

3.1 The Compound Entropy Function

ε(t) = [εmin + (εmax − εmin) · e−λt] · (1 − C) · (1 + α · sin(ωt))

Each factor serves a distinct role in the generation dynamics:

ParameterDefaultRoleEffect at extremes
εmax0.40Initial entropy ceilingAt t=0: up to 40% logit variance — forces exploration
εmin0.05Asymptotic entropy floorPrevents greedy argmax collapse; maintains 5% creative floor
λ0.08Simulated annealing rate (e−λt)Higher λ → faster convergence to base distribution
Cmax(softmax)Confidence inversion (1−C)High confidence → noise scaled down; structural integrity preserved
α0.15Pulse amplitude (sinusoidal)15% periodic entropy surge — prevents local-minima trapping
ω0.50Pulse frequency (sinusoidal)Controls cadence of creativity bursts

3.2 Simulated Annealing

The exponential decay term e−λt implements simulated annealing: generation starts in a high-exploration state (ε near εmax) and cools toward coherence as t increases. This mirrors physical annealing — early randomness explores solution space; later convergence commits to the best path. At λ = 0.08, entropy drops to within 10% of εmin after approximately 35 generation steps.

3.3 Confidence Inversion

The factor (1 − C), where C = max(softmax(base)), scales noise inversely with model confidence. When the base distribution is sharply peaked on one token (C → 1), the entropy injection approaches zero — the system preserves the mathematically obvious choice without wasting noise. When the base distribution is flat (C ≈ 1/|vocab|), entropy injection is maximized, correctly applying randomness where genuine uncertainty exists.

3.4 Sinusoidal Pulse

The factor (1 + α·sin(ω·t)) injects periodic entropy surges even as the annealing decay would otherwise suppress noise. This prevents the generation from settling into a deterministic loop prematurely — it mimics the cyclical creative-logical rhythm of expert reasoning. Critically, the sine function is deterministic given t, α, and ω — the "randomness" of the pulse is fully reproducible across all nodes.

3.5 L∞ Drift Clamp

After logit perturbation, a hard bounding constraint is applied:

perturbed = perturbed.map((v, i) => {
  let drift = Math.abs(v - base[i]);
  if (drift > 0.1) v = base[i] + Math.sign(v - base[i]) * 0.1;
  return v;
});

No perturbed logit can deviate more than ±0.1 from its base value (an L∞ norm constraint). This clamp acts as a Byzantine Fault Tolerance bounding box: even if a malicious or malfunctioning seed drives extreme noise, the output distribution cannot diverge adversarially from the base weights. It guarantees schema coherence — the generated token stream remains grounded in the base knowledge weights regardless of entropy level.

3.6 Coherence Metric

The cumulative L1 deviation from the base distribution is tracked across the generation run:

Coherence(T) = 1 − δ · Σt=0..T |perturbed[it] − base[it]|

A coherence score near 1.0 indicates generation tightly coupled to the base distribution; scores approaching 0 indicate high divergence. This metric provides a verifiable audit trail: any observer with the seed and parameters can independently compute the expected coherence and verify whether a node's output is within bounds.

4.2 Emercoin NVS as Service Registry

An inference node registers its capabilities as an NVS record under the inf: namespace prefix:

inf:node_<pubkey_hash>  →  <worm version="1.0" type="inf">
  <meta>
    <schema>ness:worm:inf:1.0</schema>
    <author>$USER_NVS</author>        <!-- privatenessID, chain-anchored -->
    <node>$NODE_NVS</node>
    <created>2025-04-09T00:00:00Z</created>
  </meta>
  <service>
    <network>tcp</network>             <!-- tcp | skywire | both -->
    <tariff>0.0001 EMC/1k tokens</tariff>
  </service>
  <inference>
    <model>llama3-8b-q4</model>
    <context_window>8192</context_window>
    <price_per_1k>0.0001</price_per_1k>
    <endpoint>/v1</endpoint>          <!-- OpenAI-compatible -->
    <skywire_pubkey>02abc…def</skywire_pubkey>  <!-- omit if inet-only -->
  </inference>
</worm>

NVS records are Write-Once-Read-Many (WORM): once written, they can only be updated by the key holder. The AuxPoW anchoring to Bitcoin makes historical rewriting economically irrational (requires a simultaneous 51% attack on Bitcoin, costing $5–20B per Coin Metrics 2024). The registry IS the index — no Hugging Face Hub, no API gateway, no centralized registry required.

4.3 Staking Economics

EMC Proof-of-Stake staking rewards subsidize node operation at the protocol level. A node staking EMC earns staking income that, with current parameters, exceeds the per-token billing overhead on typical workloads. The client sees NCH (NESS Coin Hours) as the billing unit, but the settlement path is still on-chain and pseudonymous. The network pays node operators to provide inference compute, creating a self-sustaining provider network without venture capital.

4.4 Skywire Transport

All inter-node communication uses Skywire mesh routing. The inference node's address is a Skywire public key, not a hostname or IP address. Requests route through the mesh without touching BGP infrastructure in a way that maps to a human identity. Bandwidth is paid in Coin Hours; client-facing invoices are expressed in NCH (NESS Coin Hours). The key property: there is no DNS name to block, no ASN to filter, no IP to firewall. The mesh routes around censorship at the transport layer.

5. Service Discovery Protocol

5.1 The ness: Namespace Hierarchy

ness:Root — version records, schema definitions, enumeration indexes
id:privatenessID WORM record — the trust anchor; every other record chains to this
inf:Inference node capability and pricing WORM (ness:worm:inf:1.0)
node:General node transport addresses across all networks
dns:EmerDNS records — A, SRV (TCP + Skywire), CAA for trust anchoring
rep:Node reputation attestations (specified; implementation pending)
meme:NESSMeme records for the synthetic data poisoner pipeline

5.2 EmerDNS SRV + CAA Architecture

Two NVS record types are required per node; the third is optional but strongly recommended:

CAA records are OPTIONAL. A node is fully discoverable and reachable with only SRV + WORM records. CAA adds the on-chain trust chain (operator identity → public key → TLS cert verification). Nodes without CAA are reachable but treated as unverified by compliant clients — the client connects but cannot confirm the node operator's identity. Absence of CAA is not an error; it is a disclosed trust level.
# REQUIRED — WHERE: service endpoint + port
dns:_inference._tcp.batman1.private.ness  →  "SRV 10 100 54321 batman1.private.ness"

# OPTIONAL — WHO: authorized operator identity (repurposed RFC 6844 CAA)
#   Omit for unverified / anonymous nodes. Include for verified operator trust.
dns:batman1.private.ness (CAA)            →  "0 issue \"emc:id:jeff_ness\""

# REQUIRED — WHAT: capabilities and pricing (WORM XML)
inf:node_<hash>                           →  <worm version="1.0" type="inf">...</worm>

For Skywire-only nodes, port 0 is used by convention and the SRV target is the Skywire public key. For TCP-reachable examples, use a high port such as 54321 — not 8080, which is commonly reserved by other gateway software:

dns:_inference._skywire.batman1.private.ness  →  "SRV 10 100 0 02abc…def.skywire"
dns:_inference._tcp.batman1.private.ness      →  "SRV 10 100 54321 batman1.private.ness"

5.3 CAA (Optional) — Repurposed for Sovereign Trust

CAA records are optional at the protocol level but constitute the difference between an anonymous node and a verified node. In standard DNS, CAA (RFC 6844) records name the CA authorized to issue TLS certificates for a hostname. In the PrivateNess stack, the issue tag is repurposed: instead of a CA domain, it names the NVS identity record of the node operator:

batman1.private.ness.  CAA  0  issue  "emc:id:jeff_ness"

A client verifying this node follows the chain: CAA record → id:jeff_ness NVS WORM → public key → verify node TLS/Noise certificate. The trust chain terminates at the Emercoin blockchain, not at a root CA. No DigiCert, no Let's Encrypt, no X.509 hierarchy anywhere in the path.

5.4 Discovery and Verification Flow

The minimum viable flow requires only steps 1–2 and 5–6 (SRV + WORM). Steps 3–4 apply only when the node has published a CAA record, upgrading the connection from anonymous to verified.

Query EmerDNS NVS prefix scan: dns:_inference._tcp. → list of nodes. Or read the append-only enumeration index: inf:_inference._tcp.private.ness → ["batman1","batman2",…]
Pick node per RFC 2782 priority/weight algorithm (load balancing, failover built-in)
[If CAA present — Optional] Pull CAA for target hostname: dns:batman1.private.ness → "0 issue \"emc:id:jeff_ness\"". If no CAA record exists, skip to step 5 and treat connection as anonymous.
[If CAA present — Optional] Pull id:jeff_ness NVS WORM record → operator public key. If key is absent or WORM is malformed, treat as anonymous.
Open TLS/Noise connection to SRV target:port. If CAA steps 3–4 completed: verify server cert is signed by that key; reject if it fails. If no CAA: connect without cert chain verification (anonymous node, user assumes risk).
Pull inf:node_<hash> WORM for model capabilities and pricing. Start sending tokens.
Trust levels defined:
• Verified node — has SRV + CAA + inf: WORM. Client confirms operator identity via on-chain key. Recommended for production use.
• Anonymous node — has SRV + inf: WORM only. No CAA. Client can connect but cannot verify who operates the node. Acceptable for testing or low-sensitivity tasks.

5.5 Append-Only Node Enumeration

Standard DNS wildcard queries (_inference._tcp.*.private.ness) do not enumerate nodes in DNS semantics. EmerDNS NVS supports prefix scans because it is a key-value store, not a recursive resolver. Additionally, a human-readable enumeration index is maintained:

inf:_inference._tcp.private.ness  →  ["batman1", "batman2", "gotham3"]

This index is WORM. Nodes add themselves to it; the list grows monotonically; nobody can remove entries. Append-only enumeration means the network never shrinks from the perspective of any honest observer — only grows.

6. Wiring an Inference Client — The Claude Pattern

NESS inference nodes run llama.cpp or ollama, both of which expose an OpenAI-compatible HTTP API at /v1/chat/completions. This is the lingua franca of open inference — any client built against OpenAI's API works with zero code changes, only a configuration change pointing base_url at a NESS-discovered node.

For applications currently using the Anthropic Claude API, the wiring requires a translation layer because Claude's request/response format differs from OpenAI's. Three patterns follow in increasing order of architectural completeness.

6.1 Pattern A — Direct OpenAI SDK (Zero-friction)

If your application already uses the OpenAI Python or JavaScript SDK (or any OpenAI-compatible client), the only change is base_url and api_key:

import requests
from openai import OpenAI

# Step 1: Discover a NESS inference node
def discover_ness_node(nvs_api="http://127.0.0.1:6562"):
    # Read enumeration index from Emercoin NVS
    r = requests.post(nvs_api + "/nvget",
                      json={"name": "inf:_inference._tcp.private.ness"})
    nodes = r.json()["result"]["value"]  # e.g. ["batman1","batman2"]
    # Resolve SRV for first node
    srv_key = f"dns:_inference._tcp.{nodes[0]}.private.ness"
    srv = requests.post(nvs_api + "/nvget",
                        json={"name": srv_key}).json()["result"]["value"]
    # srv → "SRV 10 100 54321 batman1.private.ness"
    parts = srv.split()
    return {"host": parts[4], "port": int(parts[3])}

node = discover_ness_node()

# Step 2: Wire OpenAI SDK to the NESS node
client = OpenAI(
    base_url=f"http://{node['host']}:{node['port']}/v1",
    api_key="privatenessID:jeff_ness"  # identity credential, not a secret
)

# Step 3: Call inference — same code as OpenAI
response = client.chat.completions.create(
    model="llama3-8b-q4",
    messages=[{"role": "user", "content": prompt}]
)
print(response.choices[0].message.content)
Authentication note: The api_key field carries the privatenessID NVS identity handle, not a secret token. The node verifies caller identity via the chain-anchored id: WORM record. There is no credential to revoke — the identity is on-chain.

6.2 Pattern B — litellm Universal Proxy (Claude→NESS)

For applications using the Anthropic Python SDK or any Claude-format API, litellm acts as a universal translation proxy. It accepts requests in any LLM API format (Anthropic, OpenAI, Cohere, etc.) and forwards them to any backend:

# pip install litellm
import litellm

# Configure once — point litellm at the NESS node
response = litellm.completion(
    model="openai/llama3-8b-q4",        # openai/ prefix = OpenAI-compat endpoint
    messages=[{"role": "user", "content": "Hello from NESS"}],
    api_base="http://batman1.private.ness:54321/v1",
    api_key="privatenessID:jeff_ness"
)

Or as a persistent proxy server that any application can point at:

# Start litellm proxy server
litellm --model openai/llama3-8b-q4 \
        --api_base http://batman1.private.ness:54321/v1 \
        --port 54321

# Now any application pointing at localhost:54321 with Anthropic SDK format
# gets transparently routed to the NESS inference node

6.3 Pattern C — MCP Tool Server (Claude as Orchestrator)

When running Claude (or any MCP-capable AI assistant) as an orchestration agent, NESS inference nodes can be exposed as first-class tools via the Model Context Protocol. The assistant calls NESS inference as a tool rather than replacing its own inference:

// ness-mcp-server.js — MCP server wrapping NESS inference
const { McpServer } = require('@modelcontextprotocol/sdk/server');
const OpenAI = require('openai');

const ness = new OpenAI({
  baseURL: process.env.NESS_NODE_URL,   // discovered from NVS
  apiKey:  process.env.NESS_IDENTITY    // privatenessID
});

server.tool("ness_inference", {
  description: "Call a sovereign NESS inference node over Skywire mesh",
  inputSchema: { prompt: "string", model: "string" }
}, async ({ prompt, model }) => {
  const res = await ness.chat.completions.create({
    model, messages: [{ role: "user", content: prompt }]
  });
  return res.choices[0].message.content;
});

The MCP configuration that wires Claude to use this tool:

// .claude/mcp.json (or claude_desktop_config.json)
{
  "mcpServers": {
    "ness-inference": {
      "command": "node",
      "args": ["ness-mcp-server.js"],
      "env": {
        "NESS_NODE_URL": "http://batman1.private.ness:54321/v1",
        "NESS_IDENTITY": "privatenessID:jeff_ness"
      }
    }
  }
}

With this configuration, Claude can explicitly delegate sensitive or sovereignty-critical tasks to NESS inference nodes while retaining its own reasoning for orchestration. The user gets the best of both worlds: Claude's capability for coordination, NESS's sovereignty guarantees for sensitive content.

6.4 Identity-Based Authentication

In all three patterns, there is no API key in the traditional sense. The api_key field carries the privatenessID identity handle (privatenessID:jeff_ness), which the node resolves against the chain-anchored id:jeff_ness NVS WORM record to verify the caller's public key. Rate limiting is identity-based, not credential-based. There is nothing to revoke, steal, or leak.

7. Security Analysis

7.1 No Prompt Logging — By Architecture, Not Policy

A centralized inference provider can say "we don't log" in their Terms of Service. This is a policy promise, verifiable only by auditing the provider's infrastructure. On the NESS stack: the inference node sees the prompt. But it has no identity to log against: Skywire transport carries no IP, and the privatenessID proves presence without revealing who. ``We don't log'' becomes structurally unenforced rather than a ToS promise. This does not remove all revocation semantics from identity keys; it removes third-party control over API-style credentials from the client path.

7.2 Censorship-Resistant Service Discovery

NVS records are WORM. Once inf:node_xyz is written, it cannot be deleted by anyone except the key holder. The AuxPoW moat means rewriting history costs a simultaneous 51% attack on Bitcoin ($5–20B, Coin Metrics 2024). Compare this to: Hugging Face can pull your endpoint in seconds, AWS can terminate your instance in minutes, Cloudflare can drop your traffic with one support ticket.

7.3 Fiber Hostile Node Resistance

The Skycoin Fiber consensus model used by NESS infrastructure has a unique property: 100% − 1 attack resistance. Even if 99.9999% of nodes are simultaneously compromised or taken offline, the last honest node with the publisher key is still a valid network. Hostile nodes cannot forge blocks without the announced publisher keys. They can delay propagation (DoS) but cannot alter the historical record (BoltDB is append-only). The floor of the network is one honest node, not a majority quorum.

8. Limitations and Open Problems

8.1 Latency

Skywire mesh routing adds hops. Consumer-class inference hardware (RK3528 class, ARM SBCs) generates tokens at 10–30 tokens/second for 7B quantized models. Combined latency makes NESS inference unsuitable for real-time interactive applications. Appropriate use cases: async workflows, batch document analysis, background generation, privacy-critical tasks where latency is a fair trade. This is a positioning constraint, not a dealbreaker — it must be stated honestly.

8.2 Model Quality Ceiling

Sovereign nodes run quantized 7B–13B models. The PrivateNess inference network is not GPT-4, Claude 3.5 Sonnet, or any frontier model. It is sovereignty-grade compute, not benchmark-grade compute. The honest pitch: you give up raw capability for unrevocability. For many use cases (summarization, structured extraction, routing decisions, privacy-sensitive content), 7B quantized at local latency is sufficient.

8.3 Provider Reputation Protocol (Open Problem)

PBAT authenticates the user. Nothing in the current stack authenticates the inference node's output integrity. A malicious node registered in NVS can serve subtly poisoned responses that pass the drift clamp. A reputation layer is specified:

rep:node_<pubkey>  →  signed attestation by <user_NVS_identity>

But the attestation signing authority is an unresolved recursion: who do you trust to sign attestations? The chain of trust bottoms out at id: records anchored on-chain, but a reputation protocol that aggregates these without centralization does not yet exist. This is the next paper after Identity Bedrock.

8.4 SRV Wildcard Enumeration

Standard DNS does not enumerate wildcard queries. EmerDNS NVS supports prefix scans, but a standard dig SRV query will not enumerate all inference nodes. Clients must use the NVS API directly for discovery, or trust the append-only enumeration index at inf:_inference._tcp.private.ness. This enumeration index itself becomes a trust-sensitive record — if corrupted (only possible by the key holder), discovery fails.

8.5 CAA Optionality and Client Enforcement

CAA records are explicitly optional in the discovery protocol. A node without CAA is an anonymous node — discoverable and connectable, but without an operator identity claim. Clients must track trust level per connection and surface it to the user: verified (CAA present, chain validated) vs. anonymous (no CAA). The hard requirement is not that all nodes have CAA — it is that clients never silently upgrade an anonymous connection to verified status. When CAA is present, verification must be enforced in the PrivatenessTools client library; skipping it on a node that published CAA is a protocol violation.

8.6 Model Availability

Some deployments may start with no local model installed. Others may run a local model or proxy to a remote backend. This does not change the trust model, but it should be stated explicitly so readers do not assume every node ships with a preloaded model.

9. Conclusion

The PrivateNess inference-as-a-service stack eliminates every attack surface of centralized AI inference through structural architecture rather than policy promises. Service discovery is WORM-anchored in Emercoin NVS with Bitcoin-level attack costs. Transport is Skywire mesh with pubkey routing that cannot be blocked at the DNS or IP layer. Authentication is chain-anchored identity with no revocable credentials. Payment is EMC microtransactions with staking economics that make node operation self-sustaining. The entropy layer is UHE-PRNG deterministic across all nodes, enabling verifiable distributed generative consensus.

Wiring any OpenAI-compatible client — including applications built against Claude/Anthropic APIs — requires only a base_url configuration change plus optional litellm proxy or MCP server for format translation. The API surface exposed by NESS inference nodes is deliberately compatible with the existing inference ecosystem to minimize integration friction.

PrivateNess inference-as-a-service: sovereign compute, mesh-routed, physically-authenticated, chain-registered, with staking economics that make the network pay you to run it — and no kill switch anywhere in the stack.

The missing piece is the provider reputation protocol. That is the next paper after Identity Bedrock.

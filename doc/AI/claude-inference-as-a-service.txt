Inference-as-a-Service on the PrivateNess Stack

The Problem Being Solved

Current IaaS (OpenAI API, Anthropic API, Together.ai, etc.) is:

Centralized auth (API keys = revocable, KYC-adjacent)

Prompt logging by default

Corporate ToS as the kill switch

BGP-reachable = geofenceable, blockable

Payment via fiat rails = traceable

The PrivateNess stack addresses every single one of those attack surfaces.

Layer Map

[ PBAT / Identity Bedrock ]   ← WHO is calling inference
        ↓
[ Emercoin NVS registry ]     ← WHERE inference nodes are, WHAT they offer
        ↓
[ Skywire mesh transport ]    ← HOW the request gets there
        ↓
[ Sovereign inference node ]  ← THE compute (llama.cpp / ollama on bare metal)
        ↓
[ EMC microtransaction ]      ← PAYMENT per token / per request

Component Roles

Emercoin NVS as the Service Registry

Prefix namespace: inf:

A node registers itself:

inf:node_<pubkey_hash>  →  {
  model: "llama3-8b-q4",
  ctx_window: 8192,
  price_per_1k_tokens: 0.0001 EMC,
  skywire_pubkey: "...",
  availability: 0.97,
  signed_by: <node_identity_NVS_record>
}

This is append-only, AuxPoW-hardened, not hosted anywhere — it is the discovery layer. No Hugging Face Hub, no API gateway, no centralized registry. The chain IS the index.

Skywire as Transport

Public-key routing, not IP routing. The request never touches BGP infrastructure in a way that maps to a human identity. Bandwidth paid in Coin Hours. The inference node you're reaching has a Skywire pubkey, not a hostname. You can't block it via DNS, firewall rules, or ASN filtering — the mesh routes around it.

PBAT as the Access Credential

The bone conduction channel is the auth token. You can't share it, delegate it, or sell it. This solves:

Credential sharing (one physical human = one PBAT)

Rate limiting without KYC (biometric rate limiting by physics, not policy)

Prompt attribution (you can prove a physical person made the request without revealing which person)

The Actarus/Goldorak principle: the pilot physically couples to the mech. No PBAT, no inference. The air-bone impedance mismatch (T ≈ 1.1×10⁻³) is your unconditionally replay-resistant session key.

EMC as Payment Rail

PoS staking rewards subsidize node operation

Net negative cost model: the same logic as NVS operations — staking income exceeds per-token billing overhead

Inference nodes that stake EMC are effectively being paid by the chain to offer compute to the network

The Killer Properties

1. No prompt logging by design, not by policy The inference node sees the prompt. But it has no identity to log against — the Skywire transport doesn't carry an IP, and the PBAT proves physical presence without revealing who. "We don't log" becomes structurally unenforceble rather than a ToS promise.

2. Censorship-resistant service discovery NVS records are WORM. Once inf:node_xyz is written, it cannot be deleted by anyone except the key holder. AuxPoW moat means rewriting history is 5× market cap expensive. Compare to: Hugging Face can pull your endpoint, AWS can terminate your instance, Cloudflare can drop your traffic.

3. Fiber hostile node resistance Even if 99.9999% of inference nodes are taken down simultaneously, the Fiber consensus model is 100%−1. The last honest node is still a valid network. This is the floor, not the average.

4. 127.0.0.1 Doctrine applied to inference Locality hierarchy:

localhost inference  →  LAN node  →  Skywire mesh node

You never hit Big Tech API unless you choose to. The preference is always the most local compute. The tattoo is the architecture.

The NESSMeme / Data Poisoner Integration

This is where it gets interesting. The memetic weapon classes plug directly into inference nodes:

NESSMeme generator: inference node generates synthetic WORM meme content, writes meme: records to NVS, propagated via Skywire

Data poisoner at inference layer: instead of poisoning training sets retroactively, you're generating synthetic data in real-time at network scale — every inference call that opts in produces poisoned output that bleeds into scrapers

The inference layer isn't just answering questions. It's an active participant in the small tech counter-offensive.

Hard Problems (hostile mode)

Latency Skywire mesh adds hops. Inference on consumer hardware (RK3528 class) is already measured in tokens/second. Combined: not viable for real-time applications. Acceptable for async workflows, batch generation, document analysis. This is a positioning constraint, not a dealbreaker — but it needs to be stated.

Model quality ceiling Sovereign nodes are running quantized 7B–13B models. The PrivateNess inference network is not GPT-4. It's sovereignty-grade, not benchmark-grade. The pitch has to be honest about this tradeoff: you give up capability for unrevocability.

NVS block time vs. load balancing EMC blocks are ~1 min. NVS-based service discovery is not suitable for sub-second load balancing across nodes. You need a second-layer routing protocol on top of Skywire for real-time node selection — NVS gives you the initial registry, but live routing needs a gossip layer.

Provider authentication (the hard one) PBAT authenticates the user. Nothing in the current stack authenticates the inference node's output integrity. A malicious node registered in NVS can serve poisoned responses. You need a reputation layer:

inf:rep:<node_pubkey>  →  signed attestation by <user_NVS_identity>

But who do you trust to sign attestations? This recurses into Identity Bedrock — the chain of trust bottoms out at id: records anchored on-chain. Solvable, but it requires a reputation protocol that doesn't exist yet and can't be faked cheaply.

The One-Liner

PrivateNess inference-as-a-service: sovereign compute, mesh-routed, physically-authenticated, chain-registered, with staking economics that make the network pay you to run it — and no kill switch anywhere in the stack.

The missing piece is the provider reputation protocol. That's the next paper after Identity Bedrock.

Architected DNS service discovery framework coupling SRV records, CAA authorization, and blockchain anchoring

Architected DNS service discovery framework coupling SRV records, CAA authorization, and blockchain anchoring

EmerDNS SRV + CAA for Sovereign Inference Discovery

The Architecture

Three record types, three jobs, all WORM-hardened on-chain:

dns:_inference._tcp.<node>.private.ness  →  SRV   (WHERE: endpoint + port)
dns:<node>.private.ness                  →  CAA   (WHO: authorized key)
inf:node_<hash>                          →  WORM  (WHAT: capabilities, pricing)

Discovery is now standard DNS semantics — any DNS-aware client, resolver, or service mesh can do it. No custom protocol, no PrivatenessTools dependency at query time.

SRV Record Structure

RFC 2782 compliant, stored as EmerDNS dns: NVS record:

_inference._tcp.batman1.private.ness.  SRV  10  100  8080  batman1.private.ness.

FieldMeaning in this contextpriorityNode tier (10=primary, 20=fallback)weightLoad balancing weight within a priority tierportInference endpoint porttargetCanonical hostname (also has A/AAAA or Skywire addr record)

Multiple nodes register under the same service name. Standard SRV client behavior gives you load balancing and failover for free, driven by priority/weight — no custom scheduler needed.

For Skywire-only nodes:

_inference._skywire.batman1.private.ness.  SRV  10  100  0  <skywire_pubkey>.skywire

Port 0 by convention when transport is not TCP. The target IS the pubkey.

CAA Record — Repurposed for Sovereign Trust

Standard CAA (RFC 6844) format:

<node>.private.ness.  CAA  0  issue  "emc:<NVS_identity_record>"

In traditional DNS, the issue tag names a CA domain (e.g. letsencrypt.org). Here you replace the CA domain with the NVS identity record of the node operator:

batman1.private.ness.  CAA  0  issue  "emc:id:jeff_ness"

This means: the only authority permitted to issue credentials for services under this hostname is the holder of id:jeff_ness in Emercoin NVS.

That record is:

Anchored on-chain (AuxPoW moat)

Append-only (can't be quietly updated by a third party)

Cryptographically bound to a keyed identity, not a corporate CA

A client verifying a node:

Resolves SRV → gets endpoint

Pulls CAA → gets the authorizing NVS identity

Pulls that id: WORM record → gets the public key

Verifies the node's TLS/Noise cert is signed by that key

The trust chain terminates at the chain, not at a root CA. No DigiCert, no Let's Encrypt, no X.509 hierarchy anywhere in the path.

Full Record Set for One Node

# Service discovery
dns:_inference._tcp.batman1.private.ness  →  "SRV 10 100 8080 batman1.private.ness"

# Address resolution
dns:batman1.private.ness                  →  "A 198.51.100.42"

# Skywire alternative transport
dns:_inference._skywire.batman1.private.ness → "SRV 10 100 0 02abc...def.skywire"

# Trust anchor — authorizing identity
dns:batman1.private.ness (CAA)            →  "0 issue \"emc:id:jeff_ness\""

# Capability + pricing metadata
inf:node_<hash>                           →  <worm version="1.0" type="inf">...</worm>

Five NVS records. One node. Fully discoverable, fully authenticated, no external authority.

Discovery Flow

client
  │
  ├─ 1. query EmerDNS: _inference._tcp.*.private.ness  (SRV enumerate)
  │       ← list of (priority, weight, port, target) tuples
  │
  ├─ 2. pick node per RFC 2782 priority/weight algorithm
  │
  ├─ 3. pull CAA for target hostname
  │       ← "emc:id:jeff_ness"
  │
  ├─ 4. pull id:jeff_ness from NVS
  │       ← pubkey + WORM identity record
  │
  ├─ 5. open TLS/Noise connection to SRV target:port
  │       verify cert is signed by key from step 4
  │
  └─ 6. pull inf:node_<hash> WORM for capabilities/pricing
          → start sending tokens

Steps 3–4 are the CAA enforcement. A node that can't produce a cert traceable to its on-chain CAA record fails step 5 — hard, before any inference traffic flows.

Hard Problems (hostile mode)

Wildcard SRV enumeration in EmerDNS _inference._tcp.*.private.ness is a wildcard query. Standard DNS doesn't enumerate wildcards — you have to know the hostname first. EmerDNS NVS can do prefix scans (list with prefix dns:_inference._tcp.) because it's a key-value store, not a recursive resolver. But a standard dig SRV query won't enumerate nodes for you. Clients need to use the NVS API directly for discovery, or you need a well-known enumeration record:

inf:_inference._tcp.private.ness  →  ["batman1", "batman2", "gotham3"]

A simple index list, also WORM. Nodes add themselves; the list grows; nobody removes them. Append-only enumeration.

CAA semantics are advisory in standard DNS In traditional DNS, CAA is checked by CAs before issuing certs — it's CA-side enforcement, not client-side. Browsers don't check CAA. In this stack, you're repurposing CAA as client-side verification, which is non-standard. Clients must be explicitly built to check it. Any client that doesn't implement the CAA check step just skips the trust anchor entirely. This needs to be a hard requirement in the PrivatenessTools client library, not optional.

CAA + Skywire addressing CAA was designed for hostname-to-CA binding. A Skywire pubkey is not a hostname. You need a defined convention for how CAA applies when the SRV target is a pubkey. Proposal: the CAA record lives on the node's NVS identity record (id:jeff_ness), not on a hostname — and the Skywire pubkey is asserted within the id: WORM. The CAA record on the DNS hostname then points to that id: record, which in turn contains the Skywire pubkey. The chain is: hostname → id: record → Skywire pubkey. One level deeper, still fully on-chain.

TTL on NVS records vs. SRV TTL semantics EmerDNS NVS records have a blockchain-level expiry (block-count-based). SRV TTL in standard DNS is seconds. A node that goes offline doesn't automatically expire its SRV record — it just stops responding. You need a liveness layer on top of discovery. Options: proof-of-liveness WORM records with timestamp updates, or Skywire transport failure as the implicit signal. Neither is built yet.

What This Gives the Wizard

The wizard needs two additional fields per node:

SRV Priority     [10]
SRV Weight       [100]

And generates two additional NVS write commands alongside the existing ones:

bash

# SRV record
EMC_SRV_KEY="dns:_inference._tcp.${NODE_HOSTNAME}"
EMC_SRV_VAL="SRV ${SRV_PRIORITY} ${SRV_WEIGHT} ${INFER_PORT} ${NODE_HOSTNAME}"

# CAA record
EMC_CAA_KEY="dns:${NODE_HOSTNAME}"
EMC_CAA_VAL="0 issue \"emc:${USER_NVS}\""

Both written to NVS. The inf: WORM XML stays as capability metadata. SRV + CAA handle transport-layer discovery and trust. Clean separation.

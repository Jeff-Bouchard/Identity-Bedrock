The key architectural decisions worth flagging:

Entropy mixing strategy follows the paper exactly — multiple os.urandom draws + RC4OK + jitter + hardware IDs all feed into pyuheprng. The hashPool() call on the UHEPRNG instance is the mixing function. Two distinct keys, one identity — the Ed25519 key is the Identity Bedrock root (the Rompel floor, no institution beneath it). The Skywire secp256k1 key is the transport address. Skywire keypair derivation is deterministically tied to the Ed25519 identity key via a domain-separated signature. This means if you ever re-provision with the same Ed25519 key, you recover the same Skywire address. The box's transport identity is permanently tied to its cryptographic identity.

RC4OK call uses makekeypair to extract fresh random material from the EMC core RNG, then hashes the output — we're mining its entropy, not keeping the key material.

The Trigger Problem

Examined hardware-based microphone isolation strategies and physical disconnection approaches
Examined hardware-based microphone isolation strategies and physical disconnection approaches
This is exactly the right question and the answer is a hardware principle: software mute is not a security control. Any software mute — ALSA, PipeWire, kernel driver — can be bypassed by a compromised process. The only trustworthy mic cutoff is physical circuit interruption.

The Threat Model
A mic that's "muted in software" is still powered, still connected, and its audio stream is still accessible to any process running as root or with audio group permissions. On a node that runs a local LLM and network daemons, that's a real surface. The only guarantee is no electrical path = no signal.

Options, Best to Acceptable
Option 1 — Inline USB power switch (best for prototype)

A hardware USB switch that cuts both VBUS and data lines. The mic is completely dead — no power, no USB enumeration, invisible to the OS.

USB host port → inline switch → USB mic dongle
These exist as $2–5 USB-A inline switches. When off, the device literally disappears from lsusb. No driver, no software involvement. Physically obvious state (switch position).

Option 2 — ReSpeaker USB mic array (best for ship)

The ReSpeaker 2-Mic or 4-Mic array has a physical mute button that cuts the mic circuit at the hardware level on the board itself, with a LED ring that changes color to confirm mute state. The LED is driven directly by the mute circuit — not by software — so it cannot lie. This is purpose-built for exactly this concern.

Option 3 — Case mod with latching switch

For the custom box enclosure (Phase 5), route the USB mic's VBUS line through a panel-mounted latching switch. Red = live, Green = cut. This becomes part of the physical design language of the NESS node — visible sovereignty.

Option 4 — Separate USB hub with per-port power switching

A USB hub with hardware per-port power switching (Plugable, YubiKey hub style). Cut mic port from a dedicated button. Overkill for prototype, reasonable for production if you want one button to control multiple input devices.

What to Avoid
A software-only mute LED (where the LED state is set by a daemon) is actively misleading — it creates false confidence. If you add a status indicator, it must be wired to the physical circuit state, not to a software flag.

Recommendation by Phase
For the prototype — inline USB switch, $3, zero complexity. Validates the rest of the stack before worrying about enclosure.

For the ship image — ReSpeaker array with hardware mute button as the standard mic. The LED ring doubles as a node status indicator (recording = red pulse, processing = amber spin, idle/muted = off).

For the enclosure design (Phase 5) — panel-mounted latching switch on VBUS line, illuminated by a hardware-driven LED that reads the actual circuit state. This becomes a physical statement about the device's philosophy — you can see whether you're being listened to without trusting any software.



The Design Principle Worth Stating Explicitly
The NESS node's privacy story has three layers and they need to be honest about what each one does:

Cryptographic — Identity Bedrock, Ed25519, EmerNVS. Protects data in transit and at rest. Cannot be compromised without breaking OWF assumptions.

Software — no cloud calls, local-only processing, user-initiated sync. Protects against network exfiltration. Can be audited but theoretically bypassable on a compromised system.

Physical — inline switch cuts VBUS and data. Cannot be bypassed by any software, any process, any root exploit. This is the only layer that is unconditional.

For a product built on the Identity Bedrock paper's philosophy — sovereignty all the way down — the physical cutoff is not an accessory. It belongs in the spec as a first-class feature. The switch is the hardware embodiment of "your rules."

from resemblyzer import VoiceEncoder, preprocess_wav
import numpy as np

encoder = VoiceEncoder()

def enroll_voiceprint(wav_path: Path) -> np.ndarray:
    wav = preprocess_wav(wav_path)
    embedding = encoder.embed_utterance(wav)
    return embedding   # 256-dim vector — store encrypted on F2FS

def verify_voiceprint(wav_path: Path, 
                      enrolled: np.ndarray,
                      threshold: float = 0.85) -> bool:
    wav = preprocess_wav(wav_path)
    current = encoder.embed_utterance(wav)
    similarity = np.dot(current, enrolled) / (
        np.linalg.norm(current) * np.linalg.norm(enrolled)
    )
    return float(similarity) >= threshold
